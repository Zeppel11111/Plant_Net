# Plant_Net 现场配网与服务器网关发现设计

## 1. 目标

课设在更换服务器电脑所连接的上游 Wi-Fi、或更换服务器电脑后，不重新编译、
不重新烧录 STM32 与 ESP32-CAM，仍能恢复传感器数据和视频推流。

现场网络采用“服务器电脑开启 Windows 移动热点”的固定拓扑：

```text
现场 Wi-Fi / 网线 / 手机网络
             │
             ▼
服务器电脑（Windows 移动热点 + Flask）
             │
       ┌─────┴─────┐
       ▼           ▼
STM32 + ESP8266   ESP32-CAM
    TCP 9000        TCP 9001
```

服务器电脑的上游 Wi-Fi 地址允许变化；设备不再依赖硬编码的热点地址
`192.168.137.1`，而是把 DHCP 下发的默认网关作为首选服务器地址。

## 2. 范围

本次只解决服务器地址随现场网络变化的问题：

- 保留 STM32 + ESP8266 上传传感器数据的现有架构；
- 保留 ESP32-CAM 独立推流的现有架构；
- 保留固定热点 SSID 和密码；
- 保留 `PN_SERVER_HOST`，将它降级为发现失败或网关连接失败时的兜底地址；
- 不引入手机 App、Web 配网页面、UDP 发现、mDNS 或新的硬件连线；
- 不处理任意第三方路由器的 SSID/密码现场录入。

## 3. 地址选择规则

两个设备使用相同的候选地址顺序：

1. 连接已配置的 Wi-Fi；
2. 从当前网络配置中取得默认网关；
3. 默认网关有效且不是 `0.0.0.0` 时，优先连接默认网关；
4. 默认网关连接失败，并且它与 `PN_SERVER_HOST` 不同，尝试
   `PN_SERVER_HOST`；
5. 两个候选地址都失败时进入现有冷却重连流程；每轮重连重新读取网关，
   以便热点重启或 DHCP 信息变化后自动恢复。

该规则同时兼容两种环境：

- 服务器电脑热点：默认网关就是运行 Flask 的电脑；
- 普通路由器：默认网关连接失败后，可回退到手工配置的
  `PN_SERVER_HOST`。

## 4. STM32 / ESP8266 设计

ESP8266 驱动新增“读取 STA 默认网关”接口。驱动发送 `AT+CIPSTA?`，逐行解析
网关字段，将 IPv4 文本写入调用方缓冲区。

接口应满足：

- 成功时返回非空 IPv4 字符串；
- 未初始化、发送失败、响应超时、字段缺失和缓冲区不足分别返回失败；
- 不修改现有 `esp8266_get_ip()` 的行为；
- 不把 AT 响应格式解析放进 App 层。

`app_uplink` 在每轮 TCP 重连时生成候选地址列表，依次尝试网关和
`PN_SERVER_HOST`。读取网关失败时，先执行一次已有的 `esp8266_auto_join()`，
成功入网后重新读取网关，再开始 TCP 候选地址连接。成功后记录实际使用的
服务器地址，日志示例：

```text
[I][app_uplink] 默认网关=192.168.173.1
[I][app_uplink] TCP 已连接 192.168.173.1:9000（热点网关）
```

本次不引入新的复杂 Wi-Fi 状态机，继续沿用现有 5 秒冷却机制；但不能只循环
执行 `CIPSTART`，网关查询确认未入网时必须重新执行已有的热点加入流程。

## 5. ESP32-CAM 设计

ESP32-CAM 完成 `WL_CONNECTED` 后调用 `WiFi.gatewayIP()` 取得默认网关。
推流任务不再只使用常量 `gw_host`，而是在建立 TCP 连接时依次尝试：

1. 当前 `WiFi.gatewayIP()`；
2. `PN_SERVER_HOST` 兜底地址。

每次断线重连前检查 `WiFi.status()`；未连接时执行有时间上限的
`WiFi.reconnect()`，重新连上后再读取网关。日志打印选中的地址和来源，避免
现场只能看到“连接失败”却不知道设备正在连接哪个 IP。

## 6. 服务端设计

Flask 及两个 TCP 服务继续监听 `0.0.0.0`：

- 传感器数据：9000；
- 摄像头推流：9001；
- 网页：8080。

服务端不需要知道电脑的上游 Wi-Fi 地址。本次不修改服务端发现协议或部署
方式；热点网卡和端口诊断脚本另立任务处理。

## 7. 异常处理

- 未取得默认网关：直接尝试 `PN_SERVER_HOST`；
- 默认网关存在但服务器未启动：连接失败后尝试兜底地址，再按冷却周期重试；
- 热点关闭：设备保持重连；热点恢复并重新获得 DHCP 后自动读取新网关；
- 热点地址变化：下一轮重连使用新的默认网关，不要求重启或烧录设备；
- 设备误连普通路由器：网关连接通常失败，随后回退到 `PN_SERVER_HOST`；
- 两个候选地址相同：只尝试一次，避免重复等待。

## 8. 验证场景

实现后至少完成以下现场测试：

1. **基准环境**：当前电脑热点下，数据和推流均连接热点网关；
2. **更换上游 Wi-Fi**：服务器电脑切换到另一个 Wi-Fi，保持移动热点开启，设备
   无需烧录并自动恢复；
3. **热点重启**：关闭再开启热点，设备重新获取 DHCP 并恢复连接；
4. **不同热点网段**：热点地址不为 `192.168.137.1` 时，两个设备仍连接实际网关；
5. **服务启动顺序**：先开设备、后开 Flask，设备能够在服务启动后自动连上；
6. **兜底地址**：普通路由器环境下，网关没有 Plant_Net 服务时能够尝试
   `PN_SERVER_HOST`；
7. **日志可诊断**：串口日志能区分网关地址、兜底地址和最终连接结果。

验收标准：更换服务器电脑的上游网络后，不修改源码、不运行配置同步脚本、
不重新烧录设备；现场只需开启约定的移动热点并启动服务器，数据与画面即可恢复。
